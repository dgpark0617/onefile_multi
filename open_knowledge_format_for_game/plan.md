/// 마리오 게임 멀티플레이 느려짐 수정 원인과 수정계획 ///

작성해주신 코드를 보니 "아, 이래서 엄청 느려졌구나!" 하고 단번에 이유가 보입니다.

결론부터 말씀드리면 질문자님의 구현 방식에 명확한 원인이 있습니다. 이전 답변에서 제가 "20명도 충분하다"고 했던 것은 데이터가 가벼운 "10초 턴제 체스 구조" 기준이었는데, 첨부해주신 코드는 완전한 "실시간 횡스크롤 액션 게임(버섯 어드벤처)"이네요!

심지어 코드 내부의 동기화 방식이 WebRTC의 성능을 극한으로 갉아먹는 형태로 짜여 있습니다. 4명만 모여도 기어 다닐 수밖에 없었던 결정적인 이유 3가지를 짚어 드릴게요.

1. 4명이 느려질 수밖에 없었던 결정적인 이유 3가지
① SYNC_MS = 50 (초당 20번의 전체 상태 방송)
JavaScript
const SYNC_MS = 50; // 50ms마다 호스트가 클라이언트들에게 브로드캐스트
호스트(방장)는 50ms마다 게임 안의 모든 데이터를 가공해서 다른 모든 클라이언트에게 쏘고 있습니다. 체스로 치면 1초에 20번씩 온 동네 사람들에게 "얘들아! 지금 폰 위치는 여기고, 보스 피는 이만큼이야!" 하고 고함을 지르는 꼴입니다.

② 무지막지한 데이터 크기 (broadcastState)
방장이 50ms마다 보내는 데이터(data)의 양이 너무 무겁습니다.

JavaScript
// 이 거대한 객체를 매초 20번씩, 3명에게 각각 쏩니다.
this.onNet({
  type: 'STATE',
  players: this.players.map(p => p.toNet()),
  coins: this.coins.map(c => ({...})),
  enemies: this.enemies.map(e => ({...})),
  bossMinions: this.bossMinions.map(e => ({...})),
  boss: this.boss ? {...} : null,
  fireballs: this.fireballs.map(f => ({ x: f.x, y: f.y })),
  ...
});
문제점: 맵에 있는 수많은 몬스터들의 좌표(enemies), 생성된 미니언들, 코인 상태, 파이어볼 좌표까지 이 방대한 리스트를 통째로 JSON 문자열로 변환(Serialization)해서 보냅니다.

JavaScript에서 이 거대한 데이터를 매초 수십 번씩 Stringify하고 파싱하는 것 자체만으로도 CPU에 엄청난 부하가 걸립니다. 4명이 모이면 호스트 컴퓨터의 브라우저가 비명을 지르게 됩니다.

③ 신뢰성 모드(reliable: true)의 역설
JavaScript
guestConn = peer.connect(remoteId.trim(), { reliable: true });
실시간 액션 게임은 데이터가 한두 개 유실되더라도 가장 최신 좌표를 빨리 받는 게 중요하므로 UDP 방식(reliable: false)을 써야 합니다.
하지만 현재 코드는 TCP 방식(reliable: true)으로 설정되어 있습니다. 이 상태에서 데이터가 조금이라도 밀리면, 브라우저는 밀린 데이터를 다 재전송받아 순서대로 처리할 때까지 다음 프레임 연산을 멈춰버립니다(Head-of-line blocking). 이것이 유저 화면에서 "지독한 버벅임(렉)"으로 체감되는 원인입니다.

2. 해결책: 어떻게 고쳐야 할까요?
만약 지금 이 실시간 액션 게임을 부드럽게 만들고 싶다면 아래와 같이 구조를 대수술해야 합니다.

변화량(Delta)만 전송하기: 전체 몬스터 배열을 다 보내지 말고, 죽은 몬스터 ID, 새로 생긴 투사체처럼 바뀐 이벤트만 가끔 보내야 합니다.

몬스터/물리는 각자 계산하기: 몬스터의 기본 이동(좌우 왔다 갔다)은 방장이 좌표를 안 쏴줘도 클라이언트 브라우저가 스스로 계산하게 만드세요. 방장은 몬스터가 '죽었을 때'만 신호를 주면 됩니다.

reliable: false로 변경: 위치 동기화 데이터는 조금 유실되어도 되니 속도가 제일 빠른 비신뢰성 모드로 패킷을 쏴야 합니다.

💡 결론: 처음에 구상하신 "10초 턴제 체스"라면?
지금 이 코드는 느린 게 당연합니다. 하지만 처음에 질문하셨던 "10초 동안 생각해서 한 번 움직이는 체스 게임"으로 전환하신다면 이야기가 완전히 달라집니다.

턴제 체스가 되면 이 무거운 loop와 50ms 주기의 broadcastState가 통째로 사라집니다.
10초에 단 한 번, 내가 움직인 "E2 to E4"라는 단 10글자짜리 텍스트만 호스트에게 쏘면 끝납니다. 20명이 아니라 50명이 접속해도 딜레이가 전혀 없을 수밖에 없는 구조가 되는 것이죠.

현재 구현하신 코드는 WebRTC 실시간 동기화의 매운맛을 정면으로 맞은 상태입니다. 실시간 게임을 고도화할지, 아니면 원래 계획하셨던 가벼운 턴제 구조로 선회하실지 결정하시면 개발이 한결 수월해지실 겁니다!
